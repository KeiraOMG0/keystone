# kick-bot: project notes for Claude

Discord bot (discord.py 2.x) + moderation web dashboard for ONE guild ("Gamer Girls HQ", ID `1530172123228930200`). Full reference: `docs/ARCHITECTURE.md`. Honeypot design contract: `docs/honeypot_contract.md` (live contract for in-flight work; do not edit it casually).

## Architecture in one screen

- **Bot process** `main.py`: loads cogs from the hardcoded `COGS` list, runs migrations, and hosts the **internal API** (`internal_api/`, FastAPI on `127.0.0.1:8766`, bearer `INTERNAL_API_SECRET`) in the same event loop. It also spawns the PO-token Node server for music (`services/pot_server_service.py`, port 4416).
- **Dashboard backend** `server/` (separate process, `uvicorn server.app:app` on `127.0.0.1:8080`): Discord OAuth2, sessions in its own `server/dashboard.db` (SQLAlchemy + Alembic), CSRF origin check, serves `server/frontend/dist`. It never touches `bot.db`; it only calls the internal API via `server/services/internal_client.py`.
- **Never create an httpx client per call in `server/`:** it costs ~280 ms here (TLS context). Use `internal_client._client()` / `supervisor_client._client()` (pooled per event loop by `server/services/http_pool.py`; `async with` does not close it). Don't add response caches for permission checks: they must stay live.
- **Two APIs, keep them straight.** Internal API = trusted, guild-scoped, no user auth, only `GET /health` is open. Dashboard backend (`/api/*`) = user-facing, does all authorization (`require_permission(...)` / `require_staff` in `server/permissions/guards.py`) and proxies to the internal API. New feature = internal route + `internal_client` method + dashboard route + frontend page.
- **Deliberate exception: the supervisor control API** (`supervisor.py`, `127.0.0.1:8767`, bearer `SUPERVISOR_CONTROL_SECRET` else `INTERNAL_API_SECRET`; ARCHITECTURE section 26). `/api/supervisor/*` (`server/routes/supervisor.py`) calls it DIRECTLY via `server/services/supervisor_client.py`, not through the internal API, so restarts work while the bot is down; it uses Diagnostics' `require_staff_even_if_bot_down`. The bot's `/restart` (`cogs/supervisor_control.py`) uses `services/supervisor_client.py` (bot code can call `await supervisor_client.request_restart(target, reason=..., requested_by="bot", source="bot")`). The two clients are duplicated on purpose; keep their contract in sync. `supervisor.py` must stay stdlib-only and import-side-effect-light (tests import it); its HTTP thread only queues requests, the main loop applies them.
- **Frontend** `server/frontend/` (React 19, Vite, Tailwind, react-query). Public routes: `/`, `/status`, `/appeal[/:token]`, `/terms`, `/hub`, `/privacy` (plus `/admin`, a redirect to the owner-only Errors tab). Everything else under `/dashboard`. The Terms of Service text lives in `pages/terms/termsContent.tsx` and must describe what the code really does: when a feature it mentions changes (auto-moderation, appeals, tickets, music, dashboard access), update it and `TERMS_LAST_UPDATED`. Same rule for the Privacy Policy (`pages/privacy/privacyContent.tsx`, `PRIVACY_LAST_UPDATED`): anything that starts storing member data, or changes a retention, cookie or third party, must be reflected there.
- **DB** `bot.db` (SQLite, aiosqlite, raw SQL in `database/repositories/`, migrations `database/migrations/sql/NNN_*.sql` registered in `main.py`'s `MIGRATIONS`, currently 1-31). Cogs call `services/`, services call repositories.
- `setup_server/` + `setup_server.py`: guild provisioning reconciler (see limitations below).

## Conventions

- **Licensing (2026-10-30, `LICENSE`, `CREDITS.md`):** the project is GPL-3.0. The birthday system is a port of NoiTheCat's BirthdayBot and stays AGPL-3.0: keep the `SPDX-License-Identifier: AGPL-3.0-only` header on its files (`cogs/birthday*.py`, `services/birthday_service.py`, `database/repositories/birthday_repo.py`) and put new code derived from it under the same header. `pot_server/` keeps its own GPL-3.0 licence. Credit any new third-party code or dependency in `CREDITS.md`. Private files (`.env`, databases, logs, `cookies.txt`, playlists, `archive/`) are kept out of the repo by `.gitignore`; extend it when something new holds secrets or member data.

- **Single guild.** `GUILD_ID` in `.env` (required; no hardcoded fallback) becomes `ALLOWED_GUILD_ID` in `main.py` (bot leaves other guilds) and `DASHBOARD_GUILD_ID` in `server/config.py`. Never hardcode a real Discord ID in code or tests: use `.env`/settings, and obvious fakes (`100000000000000001`, `123456789012345678`) in tests and placeholders.
- **Prefix is `!`** (never `$`). Config is via slash commands; moderation, `!verify`, and all music are prefix commands. Slash commands sync globally on `on_ready`. The Bot is built by `core/bot_factory.create_bot`: global `allowed_mentions` blocks @everyone/@here (opt in per send only for staff-authored, permission-gated text; today only the birthday `%e` placeholder, which only full staff (`is_staff`) may save; the birthday announcement sends `roles=False`), and every slash command is guild-only (`GuildOnlyCommandTree`). Echo user/third-party text with `AllowedMentions.none()` or `discord.utils.escape_mentions`. Prefix-command errors are handled by `core/command_errors.py` via the diagnostics collector's `on_command_error` (any such listener disables discord.py's default handler, so don't add another).
- **Bot-owned permissions, not Discord's.** `PermissionService.has_permission` (staff = `OWNER_ID` or `STAFF_ROLE_IDS` bypass everything; otherwise `permission_grants`). The permission strings: `services/permission_service.py` `VALID_PERMISSIONS` (source of truth; `cogs/advanced_commands.py` builds its choices from it), `_ALL_PERMISSIONS` in `server/routes/me.py` and the labels in `PermissionsPage.tsx`; `tests/unit/test_permission_list_parity.py` fails on drift. Self-roles/autoroles: any role in `STAFF_ROLE_IDS`, with a `permission_grants` row, with moderator perms or too high is refused at configure AND click/grant time (`services/self_role_policy.py`); new self-assign paths must use it and pass the configuring actor. The birthday role is one (anyone can register today's date): `birthday_role_block_reason` at configure time, `grant_block_reason` before `add_roles`. Permission, Settings and Roles (`/dashboard/roles`) pages use `require_staff` on purpose (prevents self-escalation).
- **Snowflakes are strings on the wire.** Internal API responses go through `stringify_snowflakes`; add new ID key names to `SNOWFLAKE_KEYS` in `internal_api/snowflakes.py`. Never `Number()` an ID in the frontend.
- **Adding a cog:** module in `cogs/` with `async def setup(bot)`, append to `COGS` in `main.py`, restart.
- **Migrations:** add `NNN_name.sql` and register it in `main.py`. Never edit an applied one. `ALTER TABLE ADD COLUMN` is not re-runnable if it half-fails.
- Settings in `guild_settings` (dashboard Settings page, `services/settings_service.py` `SETTINGS_SCHEMA`, ARCHITECTURE section 6): only `ticket_chat_logging_enabled`, `ticket_archive_purge_days` and the `antispam_*` fields are live (5s cache). Everything else applies at the next bot start: `main.py` runs `SettingsService.apply_to_config()` after migrations and BEFORE loading cogs, overwriting `config.X` with the validated saved values (never `owner_id`, which is read-only). So never import a cog or `services.ticket_service` (anything in `IMPORT_TIME_COPIES`) at the top of `main.py` or from `internal_api.app`'s import chain; a test guards this. The bot validates every write (type/range, IDs exist and are the right kind, roles assignable by the bot, templates exist; unknown keys rejected) and answers 422 `fields: {key: msg}`; `server/routes/settings.py` `_FIELD_RULES` mirrors the type/range rules, so change both together. Every change writes a `settings_update` audit row.
- Secrets live only in the root `.env` (read by both processes). `.env.example` must contain placeholders only. `cookies.txt`, `bot.db`, `server/dashboard.db`, `message_log.db` (the moderation message log: other members' messages), `user_cache.db` (departed users' profiles and who kicked/banned them), and logs are sensitive; the root `.gitignore` covers them (plus `archive/config.json`, `*.zip`, `*.7z`), and since 2026-10-30 the project is the public git repository github.com/KeiraOMG0/keystone ("Keystone", formerly kick-bot): before every commit check `git status` for anything new that holds secrets or member data, and extend `.gitignore` first.
- **Document every change.** Any agent run or edit must update the relevant docs in the same task: `docs/ARCHITECTURE.md` (tables for cogs/commands, routes, pages, migrations, env vars), `CLAUDE.md` if a convention or gotcha changed, `.env.example` for new env vars (placeholders only), and feature docs (`docs/honeypot_contract.md`, `docs/COOKIE_EXTENSION.md`). Describe the real state (built / tested / live), not aspirations, and avoid hardcoded test counts. Agent briefs must include this requirement, and the agent's final report must list what it documented.

## Run (Windows; the venv is `venv\`, already created, use it, don't create another)

```
run_bot.bat           # venv\Scripts\python.exe main.py  (bot + internal API + PO-token server)
run_dashboard.bat     # uvicorn server.app:app --host 127.0.0.1 --port 8080
server\start_tunnel.bat   # cloudflared tunnel run idlesys (dash.idlesys.xyz -> :8080)
start_all.bat         # all three, separate windows
venv\Scripts\python.exe supervisor.py   # all three under one supervisor: auto-restart, health checks, Discord webhook crash alerts (logs/supervisor/); don't mix with the .bat launchers. Autostart: install_scripts\windows\06-install-supervisor-autostart.bat
venv\Scripts\python.exe supervisor.py status | restart <bot|dashboard|tunnel|all> [reason] | rotate-logs [reason]   # talk to the RUNNING supervisor's control API
sv            # menu for the windowless supervisor; `sv help`, `sv s`, `sv health`, `sv r d [reason]`, `sv f bot`, `sv start|stop`, `sv install` (ARCHITECTURE section 26 "sv.bat")
```

`sv.bat` must keep CRLF line endings (re-convert after editing it with a tool that writes LF). `sv health` probes over HTTP, so it catches a hung dashboard that the supervisor's TCP-only dashboard check misses. Don't run `sv stop` / `sv install` / menu restarts on the user's behalf unless asked.

Supervisor notes: it takes a single-instance lock (`logs/supervisor/supervisor.lock`); a second copy logs "another supervisor is already running" and exits without starting anything. Copies started before that code existed take no lock (a stray duplicate keeps running until killed, and the tunnel has no port check, so duplicates double-connect). A `supervisor.py` change only takes effect after the supervisor itself is restarted (kill it with `taskkill /T` so its children go too, then start `kick-bot-supervisor.lnk` again; steps in ARCHITECTURE section 26). The supervisor was restarted onto the v2.0 code on 2026-10-14 (control API listening on 8767, `supervisor.py status` answers, `cogs.supervisor_control` loaded); restarts through the control API have since been used on 2026-10-14 (one requested by the owner earlier that day, and `supervisor.py restart all` at 17:43 for the fixes deploy). The dashboard's bot-down staff fallback (`require_staff_even_if_bot_down`, cached login roles) must only apply when the bot cannot answer (connection error, 5xx, guild not cached yet); a bot answer such as 404 "Member not found" is a 403. Keep that if you touch `require_staff` (it raises `from` the `InternalAPIError`) or `internal_client.check_is_staff` / `check_permission` / `check_permissions_bulk` (keep `detail`). The shared classifiers are `bot_unreachable` / `member_gone` / `cached_staff` in `server/permissions/guards.py` (diagnostics still has its own `_bot_unreachable`/`_cached_staff` copy). Same rule in the live hub (`server/live/hub.py` `resolve_access`): cached grants only while the bot is unreachable and for at most `PERMISSION_FALLBACK_MAX_AGE`; "Member not found" means no topics and the socket closes 4403. A member-gone answer is never reported as bot offline: `require_permission` and `/api/me` give 403 `not_a_member`. `/logs` scrubbing also strips appeal tokens, OAuth `code`/`state` and client IPs; restart `reason`/`requested_by` are flattened to one line. Weekly log rotation (supervisor v2.1, ARCHITECTURE section 26; live since 2026-10-14 (supervisor v2.1 running; first rotation done that day)): Mondays 04:00 local, catch-up when overdue, state in `logs/supervisor/log_rotation.json` (a first start with no state file only records a baseline; run `supervisor.py rotate-logs` or the owner-only Diagnostics "Rotate logs now" button, `POST /api/supervisor/rotate-logs` behind `require_owner`, to rotate at once); it gzips `logs/supervisor/*.log` and `bot_startup.log` into `logs/archive/<name>.<date>.log.gz` and deletes archives 28+ days old. Under the supervisor the bot no longer writes `bot_startup.log` (the supervisor sets `KICKBOT_SUPERVISED=1` and `core/logging_setup.py` then skips its duplicate `FileHandler`; stdout is already in `logs/supervisor/bot.log`), so it rotates like the others; only a bot started outside the supervisor (`run_bot.bat`) holds it open, and then it is deferred to the next supervised bot start (persisted). Never add `kicks.log` (its line 1 is the kick counter), `pot_server.log` (held by the Node child), `.pid`/`.lock` or databases to the rotator.

Start the bot before the dashboard. Do not start, stop, or restart the user's running bot/dashboard processes unless asked.

Install: `venv\Scripts\pip install -r requirements.txt -r server\requirements.txt`; dashboard DB: `venv\Scripts\python.exe -m alembic -c server\alembic.ini upgrade head` (run from repo root); PO-token server: `cd pot_server\server && npm ci && npx tsc`.

## Gotchas

- **Use `http://localhost:8080`, not `http://127.0.0.1:8080`** for the dashboard. `DISCORD_OAUTH_REDIRECT_URI` / `FRONTEND_BASE_URL` default to `localhost`, the Discord portal redirect must match exactly, and cookies are host-scoped (login loops otherwise).
- **Restart rules:** bot `.py` change -> restart bot (also restarts internal API + PO-token server); `server/**/*.py` -> restart dashboard (no `--reload`); `.env` -> restart whichever process reads it (under the new supervisor code a supervisor-restarted child re-reads `.env`; `SUPERVISOR_*` keys, and `INTERNAL_API_SECRET` when `SUPERVISOR_CONTROL_SECRET` is unset, need a supervisor restart); frontend -> rebuild only; new Alembic migration -> `alembic upgrade head` then restart dashboard.
- Dashboard shows `502 internal_api_unavailable` whenever the bot is down or restarting.
- **Live updates (WebSocket, ARCHITECTURE section 22):** the dashboard backend is the WS client of the bot's `/ws`; browsers use `/api/ws` (session cookie plus strict `Origin` from `server/csrf.py`). Cloudflare Tunnel proxies websockets, so no proxy config is needed, and same-origin makes `wss://` automatic. Restart rules: bot `.py` -> restart bot; `server/**` -> restart dashboard; a restart of either is survived (both ends reconnect forever, the browser resyncs). Uvicorn needs `websockets` (pinned in both requirements files).
- **New live page convention:** publish from the service mutation point with `services.live_events.publish(topic, data)` (never raises; add snowflake key names to `SNOWFLAKE_KEYS`), authorize the topic in `server/live/hub.py` `TOPIC_PERMISSIONS` (a tuple value = any of those permissions, e.g. `automation`), then in an `api/*.ts` hook call `useLiveTopic(topic, handler)` and set `refetchInterval: connected ? false : <old interval>` (poll only while the socket is down). Handlers must be idempotent. A NEW topic must also be added to `EVENT_TOPICS` in `services/live_events.py` (the bot rejects unknown topics) and `LIVE_TOPICS` in `src/live/protocol.ts`; add its query roots to `LIVE_ROOTS` in `src/live/LiveProvider.tsx` for reconnect resync. Anything showing guild roles should mount `useRolesLive()` / call `invalidateRoleQueries()` from `src/api/rolesLive.ts` (the `roles` topic, published by `cogs/live_roles.py`, coalesced) rather than adding its own publisher or its own `roles` handler, and add any new role query key to `isRoleQueryKey` there (it drives both live invalidation and reconnect resync). Gate the subscription on the page's main query having data (`data !== undefined`), not `isSuccess`, because a failed background refetch must not drop it. Today only Self-roles, Permissions, Roles and the Automation page's new-autorole dialog subscribe. The `stats` topic needs `staff_base` (same as `GET /api/dashboard/stats`). The QOTD/Fortnite role pickers are only invalidated and resynced, because the topic needs `manage_reaction_roles`. Exception: `diagnostics` is not invalidate-on-event but a per-connection DELTA stream (one `snapshot`, then `delta` envelopes with `set`/`unset` paths plus `rev`/`base_rev`; a client `resync` message asks for a new snapshot; ARCHITECTURE section 22 "Diagnostics deltas"). If you add a field to the dump nothing else is needed; if you change how `useDiagnostics` writes the cache, keep the base check (never merge a delta into data it was not computed against).
- **Diagnostics caches:** bot-side slow parts of the dump go through the ONE `heavy()` TTL cache in `services/diagnostics_service.py` (`TTL_*` constants, `as_of`/`ttl_seconds` or `heavy_as_of` stamps); don't add a second cache mechanism, and keep fast-moving data (CPU, loop lag, latency, net counters) uncached. `clear_caches()` (the "Clear cached data" button in Diagnostics > System, `POST /api/diagnostics/cache/clear`) must also clear any new cache you add. **psutil:** every psutil call in the bot process goes through `services/psutil_guard` (`@serialized` / `PSUTIL_LOCK`), in a worker thread, never on the event loop: concurrent psutil calls are the suspected cause of the bot's `0xC0000005` crashes in `_psutil_windows.pyd` (12 between 2026-10-10 and 10-22). `main.py` enables `faulthandler`, so a native crash leaves every thread's stack in `logs/supervisor/bot.log`; the Windows Application log ("Application Error") names the faulting module.
- **Frontend design system (`docs/DESIGN_SYSTEM.md`):** theme tokens live in `server/frontend/src/styles/globals.css` (`:root` light, `.dark` dark); use tokens (`text-danger`, `bg-card`, `border-input`), not raw colours. New pages follow the `PageHeader`/`PageContainer` pattern with skeleton, empty, error and inline-403 states and `useLiveTopic`. Geist is self-hosted via npm. Never nest `Segmented`/ToggleGroup inside a Radix DropdownMenu (froze the renderer). `useBotOffline()` disables Discord-bound buttons (not the supervisor restart buttons: those go through the supervisor, not the bot). Forms: guard unsaved edits with `useUnsavedChangesGuard(dirty)` (`src/hooks/`; `SaveBar` already does it), never a page-local `beforeunload`/click guard; global UI that navigates programmatically must go through `guardedNavigate(to, go)`. Errors: `describeApiError` (`src/lib/apiError.ts`), no per-page `formatApiError`. Query functions pass react-query's `signal` to `apiFetch`. Live handlers that another component may share invalidate via `invalidateSoon` (`src/live/invalidate.ts`). "Updates live" captions use `LiveCaption` (reflects `connected`). Staff-only (`require_staff`) nav items use `STAFF_ONLY_PERMISSION` (from `/api/me` `is_staff`), not `staff_base`. A crash anywhere shows `AppErrorBoundary` (`src/components/`, mounted in `main.tsx`; error text for a screenshot) and reports it via `src/lib/errorReport.ts` to `POST /api/public/client-errors`; it NEVER auto-reloads (the owner asked for reports instead), so keep it outermost and dependency-free and don't add reload-on-error logic. Errors (browser reports, unhandled dashboard exceptions, bot ERROR log records from `core/error_ring.py`) are listed on the owner-only Debug page's Errors tab (`?tab=errors`, short link `/admin`; ARCHITECTURE section 25). Caching: `server/app.py` serves `/assets/*` immutable for a year, `index.html` `no-cache`, missing assets `no-store`; keep that split (a cacheable index.html leaves people on deleted chunks after a rebuild). Unknown routes hit the `NotFound404` catch-all; hidden owner-only routes wrap in `OwnerOnlyRoute`.
- **Stay logged in:** sessions last 30 days sliding (`touch_session` throttled to 5 min); `/api/me` never logs out on transient failures, only on a JSON `401 unauthenticated`. Keep that when touching `apiFetch`, `useMe` or `AuthContext`. `/api/me` also returns `is_staff` (false when unknown). Cookies: `DASHBOARD_COOKIE_SECURE` defaults to `auto` (Secure on HTTPS requests, including cloudflared's `X-Forwarded-Proto` from loopback; not on `http://localhost`); `false` disables it even on the public site.
